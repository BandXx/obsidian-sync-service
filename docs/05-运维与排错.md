# 运维与排错

这份文档只写**真实踩过的坑**，每条都给报错原文和判定顺序。按出现频率排序。

---

## 1. 「远程数据库较新或已损坏」——最坑的一个

### 现象

日志里三行连在一起，看起来像网络问题，其实不是：

```
OneShot同步开始...(pullOnly)
远程数据库较新或已损坏,请确保已安装最新版本的self-hosted-livesync
无法连接到服务器
```

客户端状态栏 `↑ 0 ↓ 0`，服务器侧 access log 显示鉴权成功、`_all_docs` 返回空，但始终不写入。

### 真实机制

插件初始化时会检查远程库的版本标记文档 `obsydian_livesync_version`（注意拼写是 `obsydian`，历史遗留）。找不到时走这条路径：

```js
if (isErrorOfMissingDoc(e)) {
  const info = await db.info();
  return !(info.doc_count > 0) && await bumpRemoteVersion(...)
}
```

翻译过来：**版本文档不存在时，只要 `doc_count > 0`，就判定「这个库是别的程序建的」，拒绝初始化。**

### 为什么会被触发

为了做只读权限，提前在库里放了 `_design/permissions`。这一个设计文档就让 `doc_count = 1`，初始化从此永远走不通。用 `curl` 测读写都正常，所以极难联想到是权限设计文档导致的。

### 修复顺序（必须按这个顺序）

```bash
# ① 备份设计文档
curl -u ADMIN https://HOST/couch/DB/_design/permissions > /tmp/design-permissions.json

# ② 用 admin 删掉（普通 editor 账号删会 403）
curl -u ADMIN -X DELETE "https://HOST/couch/DB/_design/permissions?rev=REV"

# ③ 确认清空
curl -u ADMIN https://HOST/couch/DB/_all_docs   # 应为 0 行

# ④ 让客户端跑一次完整同步（生成版本文档）
#    界面点 Sync now，或命令面板执行 LiveSync: Replicate

# ⑤ 确认版本文档出现
curl -u ADMIN https://HOST/couch/DB/obsydian_livesync_version   # 200，含 version 字段

# ⑥ 再把设计文档放回去
curl -u ADMIN -X PUT https://HOST/couch/DB/_design/permissions \
  -H 'Content-Type: application/json' -d @/tmp/design-permissions.json
```

`provision-couchdb.sh` 末尾对全新空库有同样的提示。

## 2. `The remote document IDs do not match the configured ID key.`

### 现象

改完设置后整场同步被拒，`↑ 0 ↓ 0`，日志里紧跟一句 `无法连接到服务器`。

### 原因

「大小写敏感性」`handleFilenameCaseSensitive` 被打开了。

文档 ID 是路径的哈希：

```js
path2id_base(...) {
  ne && (re = re.toLowerCase());        // ne = !handleFilenameCaseSensitive
  id = hashString(hashString(ns) + ":" + path)
}
```

打开它 → 含大写字母的路径算出不同哈希 → 与服务器上既有的 13000 多个文档 ID 全部对不上 → `assessRemoteDocumentIds()` 返回 `mismatched` → 直接拒绝同步。

### 处理

**永远保持关闭。** 这条没有例外，也不存在「先打开再迁移」的平滑路径——打开等于换了一套 ID 命名空间。

## 3. 客户端连上了，但文件传不过去

先做一件事：**核对账目**，别猜。

```bash
# 服务器上有多少个文件文档
curl -u ADMIN 'https://HOST/couch/DB/_all_docs' | python3 -c "
import sys,json
rows=json.load(sys.stdin)['rows']
from collections import Counter
c=Counter(r['id'][:2] for r in rows)
print('文件 f:', c.get('f:',0))
print('内容块 h:', c.get('h:',0))
print('内部配置 i:', c.get('i:',0))
"
```

和本地文件数对比。**如果数量对得上，就不是丢数据，是源头被过滤规则静默跳过了。**

客户端过滤规则一共六条，按可能性排：

| 设置项 | 默认值 | 后果 |
|---|---|---|
| `syncMaxSizeInMB` | 50 | 超过上限的文件静默跳过，无报错 |
| `syncInternalFiles` | 关 | `.obsidian/` 完全不同步 |
| `syncIgnoreRegEx` / `syncOnlyRegEx` | 空 | 配了就被裁掉一部分 |
| `handleFilenameCaseSensitive` | 关 | 同名不同大小写只留一个 |
| `processSizeMismatchedFiles` | 关 | 传输中被改过的文件跳过且不重试 |
| 隐藏文件 / `.trash` | — | 点开头的文件被跳过 |

要「像操作一个仓库一样、不要限制」的配置见 [03-同事接入.md](03-同事接入.md)。

### 定位方法

命令面板 → `LiveSync: Show log` → 搜 `skip` / `ignore` / `too large`。这是唯一可靠的错误来源，状态栏的 `↑ ↓` 数字是上一个插件留下的，别信。

## 4. `bind_address` 改了但端口映射不生效

`POST /_cluster_setup` 的 `bind_address` 如果传 `127.0.0.1`，CouchDB 在容器内只听环回，Docker 的 `-p 5984:5984` 形同虚设，外部 `curl` 直接 `000`。

```bash
sed -i 's/^bind_address = 127\.0\.0\.1$/bind_address = 0.0.0.0/' /opt/couchdb/etc/docker.ini
docker compose restart
```

持久化位置是 `/opt/couchdb/etc/docker.ini`（挂载进容器的 `local.d` 目录）。

## 5. CORS 预检失败

Obsidian 桌面端的 origin 是 `app://obsidian.md`，不是 `http://localhost`。漏了它，`OPTIONS` 预检直接失败，表现为「无法连接到服务器」。

```bash
curl -u ADMIN -X PUT https://HOST/couch/_node/_local/_config/cors/origins \
  -H 'Content-Type: application/json' \
  -d '"app://obsidian.md,capacitor://localhost,http://localhost"'
```

验证：

```bash
curl -i -X OPTIONS https://HOST/couch/DB/ \
  -H 'Origin: app://obsidian.md' \
  -H 'Access-Control-Request-Method: GET'
# 期望 204 + access-control-allow-origin: app://obsidian.md
```

## 6. 两个不同的库同步到同一个 database name

LiveSync 按 vault 配置。两个 vault 填了同一个库名，内容会**互相合并**——A 的笔记出现在 B 里，反之亦然。这不是冲突，是设计如此：同一个库就是同一份数据。

多库必须用独立库名：

```
obsidiannotes
obsidiannotes-work
obsidiannotes-eden
```

服务器侧无需额外配置，客户端填不同 `couchDB_DBNAME` 即可，账号权限仍然生效。

## 日常运维

```bash
# 状态
docker compose -f /opt/couchdb/docker-compose.yml ps
curl -s -u ADMIN http://127.0.0.1:5984/

# 资源占用
docker stats --no-stream couchdb-livesync
free -m

# 日志（CouchDB 本身很安静，异常主要看 nginx）
tail -f /var/log/nginx/access.log | grep couch

# 重启
systemctl reload nginx
docker compose -f /opt/couchdb/docker-compose.yml restart

# 备份（导出到库外，不要只依赖客户端）
curl -u ADMIN 'http://127.0.0.1:5984/DB/_all_docs?include_docs=true' > backup-$(date +%F).json
```

## 升级

```bash
cd /opt/couchdb
docker compose pull && docker compose up -d
```

升级前先备份 `data/` 目录。CouchDB 跨大版本可能有迁移，不要在没备份的情况下跳版本。
